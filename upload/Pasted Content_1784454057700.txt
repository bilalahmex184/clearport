PROMPT 19 — Fix the Dockerfile: run the worker, and build deterministically

CRITICAL: as currently written, deploying via this Dockerfile means uploaded documents never
get processed — the worker that claims processing_jobs rows never starts in the container.

1. Decide the container topology. Simplest for your scale: run both processes in one container
   via a tiny process supervisor (or a shell script CMD that backgrounds one and execs the
   other with proper signal forwarding) — e.g.:

     CMD ["sh", "-c", "node server.js & bun mini-services/worker/index.ts & wait -n"]

   `wait -n` means the container exits (and gets restarted by your orchestrator) if EITHER
   process dies, rather than silently continuing with only one of them running — a half-alive
   container is worse than a dead one here, since it'd look healthy (HEALTHCHECK hits the
   Next.js server fine) while silently not processing anything.

   Cleaner alternative if you're open to it: two separate images/services (a `web` target and
   a `worker` target) run via docker-compose or two separate deployments — more idiomatic, more
   ops overhead. Either is fine; just pick one and make sure the worker actually runs somewhere
   whenever the web container does.

2. Fix the dependency install step. `npm install --frozen-lockfile` isn't a real npm flag (that
   silently falls through to the `|| npm install` fallback every time, which does NOT respect
   bun.lock). Since the project is bun-only now (no package-lock.json), install bun in the
   deps stage and use it for real:

     FROM oven/bun:1-slim AS deps
     WORKDIR /app
     RUN apt-get update && apt-get install -y --no-install-recommends poppler-utils openssl ca-certificates && rm -rf /var/lib/apt/lists/*
     COPY package.json bun.lock ./
     RUN bun install --frozen-lockfile

   Carry `bun` (or at least the resolved node_modules) through to the runner stage, and use
   `bun mini-services/worker/index.ts` for the worker process in that final CMD, matching
   what ecosystem.config.js already does for the pm2 path. This closes the same
   non-determinism gap that caused Prompt 18's eslint drift, in the one place it matters most
   — the actual production image.

3. Add a health check for the worker too, not just the web server — e.g. have the worker
   touch a heartbeat file or expose a tiny HTTP endpoint on a second port that HEALTHCHECK
   (or your orchestrator's liveness probe) can also poll, so a wedged worker gets restarted
   instead of running silently useless.

VERIFICATION: build the image, run it, upload a real document, and confirm it actually
transitions from queued → processing → completed inside the container — not just that the web
UI loads.


PROMPT 20 — Reconciliation for stuck processing_jobs rows

Extend the existing stuck-item reconciliation pattern (migration 013, which only watches the
old `documents.processing_status` column) to also cover the new queue. A `processing_jobs` row
can get permanently stuck in 'processing' if the worker is killed mid-job — nothing currently
retries it, dead-letters it, or alerts on it.

1. New migration: a pg_cron job (same pattern as 013) that runs every few minutes and finds
   processing_jobs rows where status = 'processing' AND claimed_at < NOW() - INTERVAL '5 minutes'

   abandoned jobs, not slow-but-alive ones). For each: if attempts < max_attempts, reset to

   with an error_history entry noting "reclaimed after worker timeout."
2. Extend /api/health/alerts (or add a third condition) to also flag processing_jobs rows
   that have been 'processing' for longer than the reconciliation window but haven't been
   swept yet — gives you a live signal, not just an eventual self-heal.

PROMPT 7 — Fix the React anti-patterns reactStrictMode was hiding

ESLint (via eslint-plugin-react-hooks) currently reports 14-15 errors, concentrated in
